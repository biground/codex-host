## 0. Ponytail：编码任务路由

- 当任务涉及编写、修改、修复、重构、评审或设计代码，选择库或依赖，或用户明确调用 Ponytail 时，使用个人独立 Skill `ponytail`；非编码任务不加载。不要把旧插件名 `ponytail:ponytail` 当作已安装能力。
- `PONYTAIL_MODE` 为 `off` 时不加载；`lite` / `full` / `ultra` 时采用对应强度，缺失时采用 Skill 默认值。用户明确指定强度或停止时，以当前指令为准。每个新任务重新判断适用范围，压缩后恢复这一判断，不把上个编码任务的启用状态带入非编码任务。
- Ponytail 只指导生产实现的简洁性与复用，不扩大写入授权、不缩减已确认的交付目标，也不限制解释长度或专业指导。测试范围遵循 `test-driven-development` 的风险判断和项目验证要求；Ponytail 的 ONE check、禁用框架或一行免测不能覆盖它们。

## 需求澄清与方案分歧

- 区分已经确认的目标、可通过项目证据查明的事实和需要用户决定的取舍。先检查可得证据，不把所有实现细节都变成问题。
- 只有歧义会实质改变目标、验收标准、架构、数据、体验、成本或安全边界时，使用 `grill-me` 澄清；常规可逆的实现选择在授权范围内自主决定，必要时说明假设。
- `grill-me` 阶段必须逐一质询关键问题；仅在确有实质取舍时提出 2-3 种可选方案，说明取舍、风险和推荐方案。
- 必要决策清楚后执行相关修改；等待关键答案期间可继续不依赖答案的只读调查和已授权工作。
- 若需求已经明确且风险低，可以直接执行，但执行前要简短说明理解和即将采取的动作。
- 除非确实需要人工干预、确认方向，或涉及高风险、不可逆操作，否则简单且低风险的任务应尽量减少与用户反复确认；在现有信息足够时，直接按判断的最优方案执行，再由用户根据结果反馈和迭代。
- 如果用户明确要求跳过讨论、直接执行或选择某个方案，则按用户的最新明确指令推进，同时保留必要的安全检查。

## 供新会话使用的任务 Prompt

- 用户需要在新会话或独立 Agent 中使用的 Prompt 时，以接收方看不到当前聊天为前提，只写接下来要执行的任务、必要输入、明确授权与约束、交付物和停止条件。
- 不夹带当前会话的历史、身份衔接或隐含指代，例如“原规划会话已结束”“接任本会话”“覆盖之前授权”“按上面讨论继续”。必要事实直接写清，必要依据给出具体可读取的文件路径、版本或其他独立输入；恢复任务也应指向实际状态记录，不要求接收方理解未提供的旧聊天。
- 交付前脱离当前聊天自检：仅凭该 Prompt 及明确列出的输入，能否确定在哪里工作、读取什么、执行什么、允许修改什么、交付什么、何时停止。删去无助于执行的过程叙述，不把当前会话的承诺或授权自动带入新会话。

## 授权与任务规模

- 解释、总结、检查和审查默认只读，在对话中返回结果；不因此创建笔记、计划或规则文件，也不触发提交、发布或外部写入。Terra 模式按下文建立必要的本地任务记录与备份登记；若用户明确禁止写入或更高优先级、项目规则不允许，则遵守该限制并说明无法持久化。用户明确要求执行、修复、保存或采纳方案后，在对应范围内完成必要工作，不重复索要已有授权。
- 先确定目标、约束和验收标准，再选择规划、检索、测试与协作方式。简单任务可直接完成；复杂任务保留依赖梳理、恢复信息和必要验证，不固定文件数、检索轮数或测试数量。
- 子代理遵循宿主工具与项目的授权规则；只为可独立界定、能验收且收益明确的子任务使用。不可用时继续主代理工作并说明实际限制，不模拟隔离或声称已委派。

## 多模型分工

### Codex 主代理与子代理

- 主代理使用当前会话选定的模型和推理档位，负责确定目标、拆分任务、整合结果和最终验收。简单任务可直接完成，能独立界定、验收且收益明确的子任务主动委派。
- 无论主代理使用哪种模型或推理档位，分析、编码、查证、测试等常规子任务默认使用 `gpt-6.1-terra / max`。用户对本次子任务明确指定的模型或档位优先。
- 内容创作、评论、总结、润色、机械复制、固定格式填充及其他文本生成由主代理直接完成；混合任务中的文本部分和 Codex 任务执行报告也由主代理直接输出。用户明确要求将具体任务委派给其他代理或模型时，按用户要求和适用的委派流程执行。
- 常规子任务通过 Codex 原生子代理派发。用户级 `config.toml` 的 `[agents]` 提供 `default_subagent_model` 和 `default_subagent_reasoning_effort`。若入口的完整历史分叉会继承主代理设置，则使用独立上下文（如 `spawn_agent` 的 `fork_turns="none"`），按此次选择传入 `model` 和 `reasoning_effort`。模型、档位或入口不可用时，报告受影响的交付物，继续其他可完成的工作；禁止静默换模型或降档。
- 派发时写明目标、必要背景、允许操作的文件范围和验收标准。只读任务禁止写入，并行写入划分文件归属。子代理只执行分配的任务，不继续委派；遇到范围或设计冲突时返回证据，由主代理裁决。
- 主代理等待子任务结束，核对实际产物、修改范围、验证结果和未完成项后交付。跨宿主委派时，将适用的权限和项目规则写入任务正文。

### Terra 主代理工作流（条件启用）

用户明确指定 GPT-6.1 Terra 为主代理，或已选择并确认当前主会话使用 Terra 时，执行以下备份和任务记录要求。子代理选择统一遵循上方的「Codex 主代理与子代理」。仅使用 Terra 作为子代理不会触发本节。

#### 修改前备份与七日待删除区

- 修改任何已有文件前，备份其当时的完整内容，确认备份可读取后才修改；包括代码、配置、文档、任务记录和备份清单，不以 Git 提交代替备份。记录源路径、备份路径、所属任务和备份时间。新文件无需空备份，但须记录新建路径。备份区使用独立目录，避免混入用户已有文件或误提交；备份操作本身不递归备份备份文件。
- 任务完成后，Terra 检查实际改动、相关验证与备份记录；确认完成且自审无误，才将本任务备份移入专门的待删除区，并逐份记录原文件、移入时间、最近变动时间和预计删除时间。中断、验证失败、审核发现问题或仍需恢复时，保留备份，不进入自动删除流程。
- 每份待删除备份从移入起单独保留至少 7 × 24 小时；期间对应原文件或备份被修改、覆盖、替换或恢复时，从最后一次变动重新计算七天。新增其他文件的备份不重置无关备份；仅查看或巡检不算变动。
- 设置系统定时任务定期检查，Windows 优先使用任务计划程序；一个任务可管理所有备份。删除前重新核对登记、变动记录和保留时间，只删除待删除区内由此流程登记且确认到期的备份；状态无法确认时保留并记录原因。关机或错过执行时，在下次成功运行时检查。定时任务无法创建或验证时明确告知并保留备份，不得声称自动清理已经生效。

- 不假设当前会话上下文完整。在项目规则允许的位置为当前任务建立或更新本地任务记录，已有项目优先沿用既有记录；关键事实、决策或状态变化时及时更新。修改已有记录前同样先备份，避免写入密码、令牌等不必要的敏感信息。

## Git 提交规范

- Commit message 必须使用中文描述清楚“做了什么”，避免 `update`、`fix bug`、`misc` 等模糊表达。
- 开头必须使用 Conventional Commits 前缀，可带中文 scope，例如：
  - `feat(行为编排): 新增可恢复 ActionFlow 管理器`
  - `fix(资源加载): 修复重复释放导致的引用计数错误`
  - `chore(规则): 补充 Codex 提交信息规范`
- 常用前缀：`feat` / `fix` / `chore` / `docs` / `refactor` / `test` / `perf`。
- 一个 commit 只表达一个主要意图；如需说明验证、风险或迁移方式，在 commit body 中继续使用中文补充。

## Git / SSH 优先路径与故障恢复

本节适用于当前任务已经授权的提交、拉取和推送，不额外扩大 Git 操作授权。

### 优先顺序

- 操作前先核对目标 remote 的协议与主机、当前分支、HEAD、upstream、工作区和暂存区。共享工作区存在其他会话修改时，按文件或 hunk 隔离本任务；本地提交完成和远端已包含提交分别验证。
- SSH 身份优先沿用用户或仓库现有的有效显式配置。必要时检查 `core.sshCommand`、`GIT_SSH_COMMAND` / `GIT_SSH`、实际 SSH 客户端及 `ssh -G <host>` 的解析结果，不能只凭当前 shell 的 `ssh` 推断 Git 使用的客户端或身份。
- **本机 `git.qintent.com` 的已验证路径（2026-11-12）：** 未有更明确、仍有效的用户或仓库身份配置时，先核对主机和密钥文件是否匹配且存在，再优先在本次 Git 子进程的环境中设置 `GIT_SSH_COMMAND` 为下列值，用于该主机的 `fetch` / `ls-remote` / `push`：

  ```text
  C:/Windows/System32/OpenSSH/ssh.exe -i C:/Users/cyt4b/.ssh/fork_ssh -o IdentitiesOnly=yes -o BatchMode=yes
  ```

  该对应关系只适用于本机和已核对的主机，其他主机不得照搬密钥。通过子进程环境限定作用范围；除非用户明确要求永久配置，不因此修改全局 Git 配置、SSH 配置或 remote。

### 常见失败的处理

- **`Too many authentication failures` / SSH 认证失败：** 先核对实际客户端、目标主机、已配置身份与公钥归属，再用匹配的现有密钥配合 `IdentitiesOnly=yes` 重试；避免 SSH agent 继续枚举无关身份，不原样反复重试。只检查必要的路径、配置和公钥指纹，不输出私钥、口令或令牌，不关闭主机密钥校验。密钥缺失、需要交互解锁或账号无目标仓库权限时，明确指出具体缺项及最小处理步骤。
- **`non-fast-forward`：** 先用已确认的身份 `fetch` 目标分支，核对本次提交是否已在远端祖先链中，并检查相关文件与产物仍然保留；并发会话可能已经推送了包含本次提交的后续提交。远端已包含且产物保留时直接记录结果，不重复提交或盲目 rebase。确需整合时，在隔离 worktree 中处理并做相关验证，保护当前未提交内容；不自动 force push、硬重置或使用 autostash 搬走其他会话改动。
- **`index.lock` / 并发 Git 写入：** 先核对活动 Git 进程、锁文件和 HEAD 的变化，等待有效写入自然结束；锁仍活动时不删除、不覆盖、不终止其他会话。仅确认锁确已遗留、没有活动写入且完成备份后，才可定点清理。使用 `GIT_INDEX_FILE` 隔离提交时，提交后还要核对普通索引；只同步可确认仍由本任务安装的索引条目，并以最新 HEAD 为准，保留其他会话的新暂存内容，避免遗留本次操作造成的反向暂存差异。
- 收尾记录实际提交 SHA、目标远端分支、命令结果和远端内容核验。认证通过后的分支拒绝按分支问题处理；本地提交成功、某次推送失败或远端存在后续提交，都不能单独作为最终同步状态的结论。已确认且仍适用的本机处理路径在后续任务中优先复用，失效时再按证据更新。
