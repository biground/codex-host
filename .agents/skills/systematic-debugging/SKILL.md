# 系统化调试

## 概述

随机修复浪费时间并引入新 bug。快速补丁掩盖了底层问题。

**核心原则：** 在尝试修复之前，务必先找到根因（root cause）。修复症状就是失败。

**违反这个流程的字面意思，就是违反调试的精神。**

## 铁律

```
在没有完成根因调查之前，不得尝试任何修复
```

先区分观察事实、根因假设与已验证结论。可以给出有依据的候选方案，但验证前不把假设写成确定根因。解释/检查任务只读；实施修复仍需任务授权。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况下使用：**
- 时间压力大（紧急情况让猜测变得诱人）
- "只是一个快速修复"看起来很明显
- 你已经尝试了多个修复
- 之前的修复没有奏效
- 你没有完全理解问题

**不要跳过：**
- 问题看起来简单（简单 bug 也有根因）
- 你很着急（匆忙保证返工）
- 领导要求立刻修好（系统化调试比反复折腾更快）

## 四个阶段

按证据需要使用下列阶段。简单问题可快速完成；复杂问题保留数据流、依赖和回归调查，不为形式遍历无关组件。

### 第一阶段：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪（stack trace）
   - 记下行号、文件路径、错误代码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都能复现吗？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查近期变更**
   - 是什么改动可能导致了这个问题？
   - Git diff，最近的提交
   - 新依赖，配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在已有日志和代码不足以定位相关边界时，按授权补充必要诊断：**
   ```
   对与故障相关的组件边界：
     - 记录必要且已脱敏的输入摘要
     - 记录必要且已脱敏的输出摘要
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次以收集证据，展示问题出在哪里
   然后分析证据以识别故障组件
   然后调查该具体组件
   ```

   只检查密钥/令牌是否设置，不输出值或完整环境变量。环境差异优先比较键名、存在性和非敏感配置；诊断不应改变签名、发布等外部状态。

5. **追踪数据流**

   **当错误深在调用栈（call stack）中时：**

   参阅本目录下的 `root-cause-tracing.md` 了解完整的向后追踪技术。

   **快速版本：**
   - 错误值从哪里来？
   - 谁用错误值调用了这里？
   - 持续向上追踪直到找到源头
   - 在源头修复，而非在症状处修复

### 第二阶段：模式分析

**在修复之前找到规律：**

1. **找到可工作的示例**
   - 在同一代码库中找到类似的可工作代码
   - 什么类似的东西是正常工作的？

2. **与参考实现对比**
   - 如果正在实现某个模式（pattern），完整阅读参考实现
   - 不要略读——逐行阅读
   - 在应用之前完全理解该模式

3. **识别差异**
   - 正常和异常之间有什么不同？
   - 列出每一个差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖关系**
   - 这需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚地陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做出最小可能的变更来测试假设
   - 一次只改一个变量
   - 不要同时修复多个问题

3. **继续之前先验证**
   - 有效吗？是 → 进入第四阶段
   - 无效？形成新假设
   - 不要在上面叠加更多修复

4. **当你不确定时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

### 第四阶段：实施

**修复根因，而非症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 如果可能使用自动化测试
   - 没有测试框架时使用一次性脚本
   - 优先在修复前建立；无法自动化时记录复现证据和手工验收缺口
   - 使用 `test-driven-development` 技能编写正确的失败测试

2. **实施单一修复**
   - 解决已识别的根因
   - 一次一个变更
   - 不要"顺手"改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 其他测试没有被破坏吧？
   - 问题确实解决了吗？

4. **如果修复无效**
   - 分析新输出，记录哪些假设被排除，下一步将验证什么。
   - 有新证据或可检验的新假设时继续；不要盲目重复，也不要因固定失败次数推断架构错误。
   - 若修复反复暴露共享状态或耦合问题，检查架构假设；超出当前范围或需关键取舍时再与用户讨论。
   - 缺少必需权限、输入或外部变化，且无法继续独立工作时，报告具体阻塞及所需帮助。

## 危险信号——停下来并遵循流程

如果你发现自己在想：
- "先快速修复一下，以后再调查"
- "试试改一下 X 看看有没有用"
- "加几个改动，跑测试试试"
- "跳过测试，我手动验证"
- "大概是 X，让我修一下"
- "我没完全理解但这可能有用"
- "模式说的是 X 但我用不同的方式适配一下"
- "主要问题有这些：[在没有调查的情况下列出修复方案]"
- 在追踪数据流之前就提出解决方案
- **没有新证据或理由，却重复同样的失败尝试**
- **每次修复都在不同地方暴露新问题**

**以上所有情况都意味着：停下来。回到第一阶段。**

怀疑架构时给出依赖或状态证据；失败次数本身不是结论。

## 你的人类伙伴发出的"你做错了"信号

**留意这些纠正：**
- "那不是没有发生吗？"——你在没有验证的情况下做了假设
- "它会告诉我们……吗？"——你应该添加证据收集
- "别猜了"——你在没有理解的情况下提出修复
- "深度思考一下"——质疑基本面，而不仅仅是症状
- "我们卡住了？"（沮丧）——你的方法不起作用

**当你看到这些时：** 停下来。回到第一阶段。

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。对于简单 bug，流程很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜测-检查-反复折腾更快。 |
| "先试这个，再调查" | 第一个修复定下基调。从一开始就做对。 |
| "我先确认修复有效后再写测试" | 未经测试的修复不可靠。先测试才能证明。 |
| "一次修多个节省时间" | 无法隔离什么起了作用。会引入新 bug。 |
| "参考实现太长了，我适配一下" | 部分理解保证出 bug。完整阅读。 |
| "我看到问题了，让我修修" | 看到症状 ≠ 理解根因。 |
| “再试一次”却没有新信息 | 先说明下一步能区分什么原因；无法区分时改变调查方式。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解了什么和为什么 |
| **2. 模式** | 找到可工作的示例、对比 | 识别出差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 已解决，测试通过 |

## 当流程揭示"没有根因"时

如果系统化调查揭示问题确实是环境相关、时序相关或外部原因：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理方式（重试、超时、错误消息）
4. 添加监控/日志以便将来调查

证据不足时保留不确定性，不把“暂未定位”写成“没有根因”。

## 辅助技术

这些技术是系统化调试的一部分，位于本目录中：

- **`root-cause-tracing.md`** - 通过调用栈向后追踪 bug 以找到原始触发点
- **`defense-in-depth.md`** - 在找到根因后在多个层级添加验证
- **`condition-based-waiting.md`** - 用条件轮询（condition polling）替代任意超时

**相关技能：**
- **test-driven-development** - 用于创建失败测试用例（第四阶段，第 1 步）
- **verification-before-completion** - 在声称成功之前验证修复有效
