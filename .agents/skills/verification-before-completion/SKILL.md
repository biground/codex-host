# 完成前验证

先有证据，再给结论。结果必须来自实际检查，不能来自信心、已改代码或其他代理的一句“成功”。

## 选择与核对证据

1. 明确要证明的行为或状态，选择覆盖受影响范围的检查；执行项目要求的必要验证。
2. 阅读检查输出和退出状态，区分通过、失败、跳过与环境阻塞。输出过长时读取相关完整日志，不能把截断等同于通过。
3. 核对需求与实际改动，以及副作用、文件归属和授权；测试通过不自动代表全部需求满足。
4. 报告实际覆盖范围和重要缺口。主代理核对子代理的产物与证据，对整体验收负责。

## 何时复用、何时重跑

- 当前任务中已有的检查，只要相关代码、输入、依赖与运行环境未改变，且仍覆盖当前声明，就可以复用。保留命令、结果及对应版本/文件状态，足以判断适用性即可。
- 新修改、失败、环境变化或未解决的疑点影响已有证据时，重跑受影响检查；跨独立任务不能未经核实直接沿用旧结果。
- 不要求每条回复、每次提交都重跑相同命令，也不要求无条件扩大到全量测试。
- 只读解释或审查按事实来源核验；没有执行请求时，不为“完成检查”写文件、改规则、提交或发布。

| 声明 | 需要的证据 | 不能替代它的内容 |
|---|---|---|
| 测试通过 | 对应测试输出、退出状态、跳过项 | “应该会通过” |
| 构建通过 | 对应构建成功输出 | Linter 或搜索通过 |
| Bug 修复 | 原症状/回归检查通过及影响范围检查 | 仅代码已改 |
| 配置生效 | 支持的读取方式或新任务实际加载结果 | 仅文件已保存 |
| 子任务完成 | 产物、范围与验收证据核对 | 子代理自报成功 |

若 Unity、外部系统或其他必需能力未获授权或不可用，完成已授权部分并明确缺口，不用静态检查冒充运行结果。
